One real preference, buried in a site's own start-up

Wait for start-up to finish ( ms), then click. The click is the freeze point — everything above is baseline, everything below is diff.

A capture taken after one click on Toggle theme must contain exactly these five entries, and no others:
entryarrivesbecause
class :root + theme-darktickedshort, enumerable, and the user caused it
class :root − theme-lighttickedits own entry — see below
ls fmnfix.theme = darktickedshort, enumerable, user-caused
ls fmnfix.analytics.lastSeenunticked13-digit number — a timestamp
ls fmnfix.clickIduntickeda UUID, and the key name says id

The removal is a separate, separately tickable entry, and it is load-bearing. This table said “four” until the differ was built and disagreed with it; the differ was right. The document is served with theme-light on every visit, so replaying only +theme-dark leaves both classes present, and here the two rules have equal specificity — source order decides, and light wins. One entry per class is also what makes trimming possible at all: six of Wikipedia's clientpref classes welded into a single tick box could not be trimmed to one.

The last two are the site writing its own state during the same interaction the user meant as a preference. They cannot be excluded by any baseline, which is precisely why the review step exists and why the question it asks is “which of these did you mean to set?” rather than “which look risky?”.

And must NOT contain any of: client-js, ready, sticky-header-visible, data-mw-ready, body.skin-vector, fmnfix.sessionId, fmnfix.locale, fmnfix.consent, fmnfix.pageviews, fmnfix.tabToken — all site-caused, all written before the user touched anything, all inside the baseline.
A diff that shows them means the baseline froze too early (or was taken at document-start, the design this one replaced).

One exception, and it is the shim, not the differ: a SECOND capture taken without reloading will also list GM:fmn_rules, GM:fmn_log and GM:fmn_trace — the first capture's own save, which under tests/gm-shim.js lands in this page's localStorage because the shim has nowhere else to put GM storage. Real GM storage is invisible to the page. Take the second capture after a reload, which is the realistic flow anyway, and the diff is clean.
